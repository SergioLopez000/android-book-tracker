# Exploration: firebase-cloud-sync

Firebase Auth + Cloud Firestore as single source of truth (option A) to add multi-device sync, cloud backup and shared book lists. Spark (free) plan. The frozen Spring Boot `backend/` is not reused.

## Current state

- Hexagonal single `:app` module. Port `BookRepository { observeBooks(sort, minRating, fromEpochDay), findById(Long), save(Book): Long, delete(Long) }`.
- `Book.id: Long?`. Room v1 `books.db` (`BookEntity` autogenerated `Long` id; `dateFinishedEpochDay: Long`; `rating: Float`).
- `BookDao` filters in SQL (`rating >= min AND (from IS NULL OR date >= from)`) with two sort queries. `GetBooksUseCase` resolves `DateRangeFilter` to an epoch day.
- The `Long` id runs end to end, including navigation (`NavType.LongType`, `NO_BOOK_ID = -1L` in `MainActivity`), UI tags `book_list_item_$id`, and the e2e regex `^book_list_item_(\d+)$` (`e2e/src/pages/tags.ts`).
- CI: gating unit tests and secret scan (gitleaks); e2e is non-gating, runs in airplane mode with `clearApp` per test. Secrets policy: nothing secret in the repo; `local.properties` is gitignored.
- AGP 9.5.3, Kotlin 2.4.21, KSP 2.3.14, minSdk 26, lint `warningsAsErrors`.

**Unit tests**

**e2e (non-gating)**

## 2. Query semantics

- **Recommended:** one snapshot listener on `users/{uid}/books`, with filter and sort in a pure Kotlin function (port the `BookDaoTest` cases; stable sort with an explicit tie-break). No composite indexes; one listener shared across filter changes, so filter changes do not re-bill reads. The port signature stays unchanged.
- **Alternative:** server-side queries. Multi-field range filters are supported, but need composite indexes per `orderBy`, re-attach the listener on every filter change, and offline queries run only against the cache.
- Offline persistence is on by default (100 MB cache, last-write-wins).
- `save()` must not await the server ack, because the write `Task` resolves only on server ack and would hang the UI offline. Verify in the spike.
- Spark quota: 50K reads / 20K writes / 20K deletes per day, 1 GiB. A listener offline for more than 30 minutes is billed as a new query on reconnect.

## 3. Room data migration

- One-time import on first sign-in: read all DAO rows, assign a deterministic UUID (for example UUID v5 of `legacy:{rowId}`), and write with `WriteBatch` (≤ 500 ops) into `users/{uid}/books/{uuid}`. Deterministic ids make a retried import idempotent.
- Completion marker both locally and as a field on `users/{uid}`.
- Keep Room read-only for one release, then remove Room and KSP in a final slice. No Room v2 migration is needed.
- Edge cases: the account already has cloud data (merge vs skip); two legacy devices duplicate books unless deduplicated by content hash.

## 4. Auth

- Firebase Auth + Credential Manager (`credentials`, `credentials-play-services-auth`, `googleid`; docs show 1.3.0 / 1.3.0 / 1.1.1, re-verify at implementation). Flow: `GoogleAuthProvider.getCredential(idToken)` → `signInWithCredential`. Requires the Web client ID (`default_web_client_id`) and the app SHA-1 in the Firebase console.
- Signed-out options:
  - (a) Sign-in required. Simplest; blocks offline first run and the current e2e suite.
  - (b) Anonymous auth + `linkWithCredential` on Google sign-in. **Recommended.** The uid is preserved; data is lost on uninstall until linked; first launch needs network.
  - (c) Local-only until sign-in. Duplicates storage logic and contradicts Firestore as single source of truth.
- Scope the repository by uid via `flatMapLatest`. Sign-out must call `terminate()` + `clearPersistence()` to avoid leaking cached documents to the next user.

## 5. Shared lists (no Cloud Functions)

- Layout:
  - `users/{uid}/books/{id}`
  - `lists/{listId}` `{ ownerUid, name, ... }`
  - `lists/{listId}/members/{uid}` `{ role: viewer | editor }`
  - `lists/{listId}/books/{id}`
  - `invites/{code}` `{ listId, role, expiresAt, maxUses, uses }`
- **Copies, not references** (recommended): simpler rules, no cross-user reads of the personal collection, no leak of private `review` text. Cost: copies drift from the original book.
- Join: one batched write that creates the member document and increments the invite's `uses`; rules check that the invite exists, is unexpired and the role matches. Use a members subcollection, not a shared `memberUids` array, so an invitee cannot rewrite other members.
- Role checks use `get()` in rules: billed as reads, at most 10 per request.
- Firebase Dynamic Links are deprecated → App Links (needs a hosted `assetlinks.json`) or code entry only.
- Leave/revoke surfaces as permission-denied on the member's listener; the UI must handle it. Deleting a list requires a client-side cascade.
- The Spark quota is project-wide: a hostile member could exhaust writes. Mitigation: App Check (Play Integrity) and size caps.

## 6. Security rules, testing, CI, secrets, e2e

- Rules: `users/{uid}/**` owner-only with field validation (`keys().hasOnly`, rating half-step 0.5–5, types, sizes); lists gated by member and role. Risks to cover: role escalation, invite replay and guessability, quota exhaustion.
- Testing: Emulator Suite via `firebase emulators:exec` + `@firebase/rules-unit-testing` (Node), allow/deny matrix per role. Android emulator access via `useEmulator("10.0.2.2", 8080)` with persistence disabled.
- `google-services.json`: Firebase documents it as non-secret identifiers, but it conflicts with the repo secrets policy, gitleaks may flag the `AIza` key, fork/Dependabot builds have no CI secrets, and the plugin fails the build when the file is missing. Recommended: commit a placeholder for CI and unit builds; keep the real file local or release-only; restrict the API key by package name and SHA-1.
- e2e: first anonymous sign-in needs network but CI runs in airplane mode → test-only wiring (in-memory repository or emulator); relax the tag regex from `\d+` to `[A-Za-z0-9_-]+`.

## 7. Dependencies and build

- Firebase BoM 35.2.0 (released 2026-11-11), google-services plugin 4.6.0, `firebase-auth`, `firebase-firestore` 27.2.0 (BoM-managed), optional `appcheck-playintegrity`.
- Official docs state AGP ≥ 7.3.0 and say nothing about AGP 9 or built-in Kotlin; a secondary source claims compatibility from plugin 4.4.2.
- **Not confirmed for AGP 9.5.3 → mandatory build spike** (plugin + placeholder JSON, then `assembleDebug` and `testDebugUnitTest`). Expect lint baseline or suppression work under `warningsAsErrors`.

## Recommendation

Firestore as single source of truth with client-side filter/sort, anonymous auth linked to Google, and copy-based shared lists. Keep Firebase types behind a thin `BooksRemote`-style interface so adapters are testable on the JVM under Strict TDD. Start with the slice 0 spike, then slice 1.

## Open product decisions

1. Signed-out behavior: (a) sign-in required, (b) anonymous + link, (c) local-only until sign-in.
2. Import policy: automatic vs ask; merge vs skip when the account already has cloud data; keep Room read-only one release vs delete immediately.
3. Sign-in methods: Google only vs Google + email/password.
4. Share model: copies vs references; whether members can edit or delete others' books.
5. Share mechanism: code entry vs App Links; invite expiry and max uses; whether anonymous users may join.
6. Roles: viewer / editor / owner; ownership transfer; member cap.
7. Fields exposed in shared lists: include `review` or not.
8. `google-services.json` policy: real file + gitleaks allowlist, CI secret, or placeholder in repo.
9. CI and e2e: gate rules tests in `ci-gate` or keep them local; e2e strategy while auth is introduced.
10. Account and data deletion (Google Play requirement for in-app accounts): in scope or deferred.
11. Spark guardrails: ship without Functions-based moderation or rate limiting; App Check; budget alerts.
12. Conflict semantics: last-write-wins acceptable.

## Risks

- google-services plugin on AGP 9.5.3 has no official compatibility statement.
- Slices 1 and 5 may exceed the 800-line budget.
- `google-services.json` vs secrets policy, gitleaks, and fork/Dependabot builds.
- e2e breaks on the numeric id regex and on airplane mode combined with auth.
- Project-wide Spark quota abuse; rules are the only server-side enforcement.
- Offline `save()` hang if the server ack is awaited.
- Cross-user cache leak if persistence is not cleared on sign-out.
- Anonymous accounts lose data on uninstall until linked.
- Duplicate books when importing from two legacy devices.
- `MainActivitySmokeTest` needs Firebase test config or an injectable container.

## Test implications (Strict TDD)

- Pure JVM first: filter/sort function (port `BookDaoTest` cases), legacy id generation, import mapper, role permission model, invite validation; ViewModel tests with string-id fakes; adapter tests against a fake `BooksRemote`.
- Emulator rules tests: allow/deny per role, field validation, invite expiry and replay, cross-user denial.
- Keep Room tests until the import slice is green.
